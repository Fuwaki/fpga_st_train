# v7 — 输入精度：RGB565 够不够，能不能更低

日期 2026-10-21 · 承接 `v6-tiny-dw-in-film.md`。
问题：风格迁移里内容图的颜色是否可有可无？输入从 RGB888 降到 RGB565 / RGB444 / 灰度，
对交付模型（`deliverables/*/vangogh`，tiny_dw `film_both`）分别值多少 dB？

**这一版没有改模型、没有重训。** 全部是拿已交付的 fp32 权重做的 PTQ 与整数参考解释器实验。
所有数字都是 `src/intref.rs`（= FPGA 行为）或 `--mode sim`（伪量化）实测，分辨率 384 长边，
6 张 `style-transfer/demo_inputs`；标注 "held-out" 的另用 `style-transfer/data/content` 的前 24 张。

---

## 0. 先给结论

1. **RGB565 基本免费。** 现有 W8A8 交付模型只掉 **0.13 dB**（26.13 → 26.00）。
   原因很直接：它的第 0 个量化点 scale 是 `1/127`，**输入本来就只有 7 bit/通道**，
   RGB888 与 RGB777 两种输入跑出的 PNG **逐字节相同**（6 张图 max|Δ| = 0）。
2. **RGB444（12 bpp）是实用下限**，代价 0.4–0.6 dB。RGB332 开始掉 2 dB，灰度掉 2.4 dB。
3. **颜色不是"不重要"，只是它的损失被量化噪声盖住了。** 在接近无损的激活精度（A16）下，
   单独把输入换成灰度会掉 **15.8 dB**（45.13 → 29.38），输出色度与输入的相关系数从 0.998 掉到 0.46。
   亮度/形状几乎不掉（luma 相关 0.99，lapvar 比 1.04）。
   也就是说：**形状靠亮度，风格靠色度，色度是学生从内容图里搬过来的，不是凭空生成的。**
   （教师侧同结论：MicroAST 灰输入下平均饱和度 0.414 → 0.401，几乎不变，
   但色度结构的相关掉到 0.35–0.82。）
4. **调查中发现两个比输入位宽重要一个数量级的问题**（§4）：
   - `up3.0.dw.in` 这个点用 min-max 标定被长尾撑爆，A8 下**只改这一个 scale** 就白拿 **+4.5 dB**
     （demo 21.64 → 26.13，held-out 24 张 20.72 → 25.39，256–640 px 全平；W4A8 +2.6 dB）。
     它的 absmax 随标定 batch 数从 12.5 跳到 25.4，说明这是**方法问题**，换一批数据还会重演。
   - `deliverables/*/vangogh_lut_dw` 的整数交付**输出常数图**：6 张内容图逐字节相同、
     每个像素都是 RGB(64,78,98)。`metrics.json` 里那句 `fp32_vs_int 17.73 dB` 就是它——数字看着像
     "能用的低分"，实际是坏图。**这条交付路径目前不可用。**

## 1. 输入格式与量化方法

`--mode fp32`（fp32 权重）与 `--mode int`（intref）都吃 PNG，所以输入格式用预生成的图模拟：
BT.601 全范围编码 → 每通道均匀量化到 `n` bit → 解码回 RGB8 PNG。
灰度为 BT.601 亮度后 1/2/3/4/6/8 bit。420 是 Cb/Cr 先 2×2 box 下采样再量化，
整数部分（RGB 通道、灰度）与 YCbCr 分开看。

代码在 `/tmp/inp_exp/gen.py`、`gen2.py`、`gen_ho.py`（一次性脚本，不入库）。

## 2. 实测：输入精度 → 输出保真度

### 2.1 已交付 W8A8 整数路径（与 fp32 + RGB888 比）

（`up3.0.dw.in` 的 scale 已按 §4.1 修正，其余不动；"luma 相关"等三列也是直接对 fp32+RGB888 的输出算的。）

| 输入 | bpp | PSNR | RMSE/σ | luma 相关 | lapvar 比 | 输出色度相关 |
|---|---|---:|---:|---:|---:|---:|
| RGB888 | 24 | 26.13 dB | 36.4 % | 0.935 | 1.89 | 0.905 |
| RGB777 | 21 | 26.13 dB | 36.4 % | 相同 | 相同 | 相同 |
| RGB565 | 16 | 26.00 dB | 37.1 % | 0.933 | 1.90 | 0.902 |
| RGB444 | 12 | 25.57 dB | 39.1 % | 0.923 | 1.93 | 0.891 |
| YCbCr 4:2:0 8bit | 12 | 26.13 dB | 36.4 % | 0.935 | 1.90 | 0.906 |
| RGB332 | 8 | 24.17 dB | 46.1 % | 0.913 | 1.64 | 0.784 |
| 灰度 8bit | 8 | 23.76 dB | 48.8 % | 0.929 | 1.78 | **0.385** |

（`lapvar 比 ≈ 1.9` 是 A8 量化噪声把纹理能量推高了约一倍，不是输入造成的；
要看输入本身的影响，看 §2.2 的 A16 那一组。色度一列才是输入降级真正的签名。）

**RGB888 → RGB777 逐字节相同**，因为 manifest 的 `point_scales[0] = 0.007874016 = 1/127`：
`intref` 把输入 `round(x/scale)` 截到 `[0,127]`，所以 8 bit 的尾位在进网络前就被扔了。
这条可以直接用：

```bash
fpga_st_train infer --model deliverables/w8a8/vangogh --content <rgb888>  --out /tmp/a --mode int
fpga_st_train infer --model deliverables/w8a8/vangogh --content <rgb777>  --out /tmp/b --mode int
# 6 张图逐字节相同
```

### 2.2 隔离输入损失：激活接近无损（A16，W8）

A8 的误差底噪（≈25 dB）会把输入的影响盖住。把激活放到 16 bit（校准后伪量化，`--mode sim`），
剩下的就几乎只有输入损失：

| 输入 | bpp | PSNR | RMSE/σ | luma 相关 | lapvar 比 | 色度相关 |
|---|---|---:|---:|---:|---:|---:|
| RGB888 | 24 | 45.13 dB | 4.2 % | 0.999 | 1.01 | 0.998 |
| RGB565 | 16 | 39.69 dB | 8.6 % | 0.994 | 1.04 | 0.996 |
| RGB444 | 12 | 32.48 dB | 19.1 % | 0.973 | 1.25 | 0.983 |
| RGB332 | 8 | 27.52 dB | 33.9 % | — | — | — |
| 灰度 8bit | 8 | 29.38 dB | 33.1 % | 0.990 | 1.04 | **0.464** |

读法：**亮度/结构到灰度都还在（相关 0.99），掉的全是色度。**
灰度那一行 33 % 的 RMSE/σ 与 0.99 的 luma 相关并存，就是这个意思。

### 2.3 输入码本深度：在 A8 噪声底之下，砍到 4 bit/通道也没差

把第 0 点的 scale 改成 `1/(2^n-1)`，等于把输入码本直接压到 `n` bit/通道
（8 bit 数据通路不变，只是网格变粗）：

| 输入位宽 | RGB565 输入 | RGB444 输入 |
|---|---:|---:|
| 7 bit/ch（现状，127 级） | 25.92 | 25.74 |
| 6 bit/ch | 25.91 | 25.83 |
| 5 bit/ch | 25.91 | 25.65 |
| 4 bit/ch | 26.02 | 25.84 |
| 3 bit/ch | 25.12 | 24.83 |

**7 → 4 bit/通道在这条 8 bit 激活路径上读不出差别**（±0.2 dB，就是量化噪声的抖动）。
原因不是"颜色不重要"，是 **A8 的噪声底（约 25 dB）比输入的 4 bit 噪声高 20 dB 以上**，
输入先被掩蔽了。这条不能当成"4 bit 够用"的证据：一旦把激活修好（§4.1）抬到 A12，
RGB444 立刻掉到 30.31（对 34.96），灰度掉到 26.24。

所以正确的说法是：**输入位宽的预算取决于激活位宽。** 停在 A8 就别在输入端花钱；
要走 A10/A12，输入至少要 12 bpp（RGB444 或 YCbCr 420）。

### 2.4 颜色到底从哪来

在 RGB888 输入的 fp32 输出上，用输入色度线性回归输出色度（2→2 线性映射）：

| 内容图 | 输出色度 R² |
|---|---:|
| animal | 0.870 |
| city | 0.864 |
| landscape | 0.743 |
| portrait | 0.739 |
| water | 0.650 |
| cat（原图是灰度） | 定义域为空 |

65–87 % 的输出色度由输入色度线性解释。教师侧同样：
MicroAST 在灰度输入上输出饱和度只从 0.41 掉到 0.40，但**色度图与 RGB 输入下的相关系数
掉到 0.35–0.82**（cat 是灰度原图，所以是 1.00）。
结论：**风格是"色调滤镜"（这一步确实几乎与输入颜色无关），但内容的结构性色偏是搬过来的。**
所以"只用明暗和形状"能拿到风格，拿不到原图的色彩关系——如果想保留一点原图色彩，
应该走 **YCbCr 420，而不是灰度**：同样 12 bpp，色度相关 0.906 对 0.385，PSNR 26.13 对 23.76。

## 3. 激活位宽才是真瓶颈（同一个 p9 修正下）

`up3.0.dw.in` 的 scale 修好之后（§4.1），W8 权重、逐档重新标定的曲线：

| 激活 | RGB888 | RGB565 | RGB444 | 灰度 8 |
|---|---:|---:|---:|---:|
| A8 | 26.13 | 26.00 | 25.57 | 23.76 |
| A10 | 30.37 | 30.08 | 29.04 | 25.51 |
| A12 | 34.96 | 33.38 | 30.31 | 26.24 |
| A14 | 36.93 | — | — | — |
| A16（未修 p9） | 45.13 | 39.69 | 32.48 | 29.38 |
| A16（修 p9） | **37.26** | 34.09 | 30.52 | 26.33 |

**A8 → A10 值 4.2 dB，A10 → A12 再 4.6 dB；输入 24 → 12 bpp 只值 0.4–4.7 dB（越往上越明显）。**
精度预算应该花在激活上，不是输入上。

**注意 A16 那两行**：p9 的 ×0.1 在 8–12 bit 上值 4–5 dB，在 16 bit 上反而**掉 7.9 dB**
（`up3.0.dw.in` 的真实 absmax 约 25，缩到 2.54 后超过 2.54 的样本被削）。
这说明 p9 不是"scale 标错了"，而是**该点的最优截断阈值随位宽变化**：
低位宽时分辨率 >> 范围，高位宽时反过来。正确的修法仍是 §4.1 末尾说的逐点直方图 MSE 阈值，
一个固定倍数只能覆盖一个位宽档。


### 3.1 逐层权重位宽（在 A8 + p9 修正上）

做法：不动打包（仍一码一字节），只把某一组层的码重新量化到 4 bit 的网格上——重算 per-channel
scale、`requant` 和 `bias_int32`，`weights.bin` 原地改写。所以这里量的是**精度**，
不是存储（存储见 §5 最后一条）。

| 变化 | 该组权重 / 全部 | PSNR |
|---|---:|---:|
| 全 8 bit（基线） | 22 736 | 26.13 |
| `stem`+`enc.*` 全 4 bit | 7 872（34.6 %） | 25.14（−1.0） |
| `enc.{0,1}` 的 4 层（不含 stem） | 7 008（30.8 %） | 25.17（−1.0） |
| 所有 1×1（含 `head.pw`）全 4 bit | 18 632（81.9 %） | 24.04（−2.1） |
| 只有 `up3.0.pw`+`up3.1.pw` 4 bit | 4 224（18.6 %） | 25.91（−0.2） |
| 只有 `up3.*.dw`+`head.dw` 4 bit | 1 224（5.4 %） | 25.18（−1.0） |
| 只有两个 res `dw` 4 bit | 1 152（5.1 %） | 26.56（+0.4，噪声） |
| 只有 `head.pw` 4 bit | 72（0.3 %） | 24.82（−1.3，**最差**） |

A12 下编码器 4 bit 是 32.44 对 35.55（−3.1 dB）。
`head.pw` 是 24→3 的输出投影，位宽最敏感，别动它；`up3.*.pw` 便宜得像白送。

## 4. 调查中发现的两个 bug（重要）

### 4.1 `up3.0.dw.in` 用 min-max 标定，在 A8 上亏 4.5 dB

交付的 `calibration.json` 里 `up3.0.dw.in` 的 absmax 是 **25.44**（scale 0.2003）。这个 absmax
本身是真的，但它**极不稳定**：同一批 demo 图，1 个 batch 是 12.5，5 个 batch 是 15.4，20 个 batch 是 24.8，
交付那次是 25.44。也就是说这个张量是**重尾**的，min-max 把 127 个码全铺给了几乎不会出现的长尾，
而它同一批图里的典型幅值只有约 2.5（`res` 输出 absmax 0.43，H/2 skip 1.50）。

逐点扫这个 scale（×0.05 … ×0.5，其余全不动）：

| 该点 scale 倍数 | 输出 PSNR |
|---|---:|
| ×1.0（交付值） | 21.76 |
| ×0.5 | 22.02 |
| ×0.25 | 24.34 |
| ×0.1 | **26.10** |
| ×0.05 | 25.26 |

另外 16 个点没有一个有这个幅度（第二敏感的 `head.pw.in` 收窄只从 21.75 掉到 16.94，是变差）。

W4A8 上同样有效：交付 20.56 → 23.15 dB（同一套 ×0.1）。

**机理**：这个点是 `upsample(trunk) + half_skip` 的和，absmax 由 trunk 的长尾决定，
但随后立刻进 InstanceNorm，IN 把均值和尺度重新归一化——所以**绝对范围在这一点上几乎不值钱，
码本分辨率才值钱**。per-tensor 对称 min-max 在重尾张量上把 127 个码全花在尾部，有效位只剩 ~4 bit。
这也解释了 v4 里"4 bit 激活误差是均匀的、收窄全局范围救不回来"的经验：
问题不在全局 safety，在**单个点**——而且 min-max 的尾部和典型值差一个数量级时才会显形。

**只需要改一个数**（已交付的 `calibration.json` 即可，不用重训、不用重新标定）：

```python
c = json.load(open("deliverables/w8a8/vangogh/calibration.json"))
c["scales"][9] *= 0.1          # up3.0.dw.in
json.dump(c, open("calibration-p9.json", "w"))
```
```bash
fpga_st_train export-int8 --model deliverables/fp32/vangogh \
    --calibration calibration-p9.json --out /tmp/quant-p9
fpga_st_train infer --model /tmp/quant-p9 --content <imgs> --out /tmp/out --mode int
```

实测（intref，与 fp32+RGB888 比）：

| | demo 6 张 | held-out 24 张 |
|---|---:|---:|
| 交付的 scale | 21.64 dB / 61.3 % | 20.72 dB / 65.0 % |
| 只改 p9 | **26.13 dB / 36.4 %** | **25.39 dB / 38.1 %** |

分辨率 256 / 384 / 512 / 640 px 分别是 25.96 / 26.13 / 25.98 / 26.01 dB，没有分辨率依赖。
（顺带：交付的 `metrics.json` 写的 21.64 dB 与此完全一致，不是测量口径问题。）

**建议**：`calibrate` 的 `--safety` 现在是全局一个数，应该改成逐点从激活直方图算 MSE 最优阈值
（或者至少对"后面接 InstanceNorm 的点"单独处理）。这条是 v5 §7 第 3 条一直没做的事，
现在有了明确的证据说明它值多少。

### 4.2 `vangogh_lut_dw` 的整数交付输出常数图

```bash
fpga_st_train infer --model deliverables/w8a8/vangogh_lut_dw \
    --content ../style-transfer/demo_inputs --out /tmp/lut --mode int
```

6 张图的输出**逐字节相同**，每张只有 **1 种颜色**（每个像素都是 RGB(64,78,98)，即整幅一个常数场）。
`w4a8/vangogh_lut_dw` 同样（RGB(64,77,92)）。`metrics.json` 的 `fp32_vs_int 17.73 dB` 就是这个常数场对
各种 fp32 输出取的平均——17 dB 看着像"低一档的质量"，实际是坏图。

根因 1（已定位）：**LUT 编码器的第 0 个量化点从来没被标定过。**
`calibrate` 打印 `image  absmax 0.00000  scale 0.000010`——`TinyDwStudent::encode_with_observe`
在 LUT 分支里 `observe` 从 `1` 开始，第 0 点（`image`）永远不观测；
`export` 又把这一路 stem 的 `in_scale = 1e-5` 原样写进 `point_scales[0]`，
于是每个像素 `round(x / 1e-5)` 全被 clamp 到 127 → 常数。

把 `point0` 手工补成 `1/127` 后：输出恢复正常（561 种颜色），但 **`fp32 vs int` 仍只有 17.96 dB**，
而 `sim vs int` 只有 21.4 dB——按 `docs/deliverables.md` §6 的判据
（"int vs sim 必须远高于 int vs fp32，掉下来就是导出有 bug"），**LUT 路径还有第二个 bug**，
manifest/权重与训练前向描述的不是同一张图。这一版没有继续往下查。
**在查清楚之前，`deliverables/*/vangogh_lut_dw` 不应对外交付。**

## 5. 硬件账：输入位宽到底省了什么

前提：流式（line-buffer）数据通路，640×480，A8 特征。

| 项目 | 值 |
|---|---|
| 全部 line buffer，输入 24 bit | 516.9 KiB |
| 输入 → 16 bit（RGB565） | 511.2 KiB（**−1.1 %**） |
| 输入 → 12 bit（RGB444） | 508.4 KiB（−1.6 %） |
| 输入 → 8 bit（灰度） | 505.6 KiB（−2.2 %） |
| 输入不变，特征 A8 → A5 | 329.4 KiB（**−36.3 %**） |
| 输入 8 bit + 特征 A4 | 255.6 KiB（−50.5 %） |

- **line buffer 是特征图占的，不是输入占的。** 输入降 24→8 bit 只省 2 %。
- 640×480 一帧：RGB888 900 KiB，RGB565 600 KiB，RGB444 450 KiB。30 fps 分别是 27 / 18 / 13.5 MB/s，
      对任何 DDR 都是零头。**省输入位宽的理由是 pin 数、ADC/sensor 接口、第一级带宽，
      不是 line buffer 或外存。**
- **stem 是 16.9 % 的 MAC、3.8 % 的权重**；把输入砍到 1 通道最多省 11.3 % 的 MAC
  （334.8M → 297.1M @256²）。7 个 1×1 点卷积是 **64 % 的 MAC、82 % 的权重**——
  想给 FPGA 减负，那里才是主战场，不是输入。
- 省比特 **不是均匀省钱**：`i4-x2` 一字节两码只对 4/8 bit 成立（`pack_weight_codes` 对 6 bit 直接 panic，
  实测 `export-int8 --bits w6a8` 崩在 `no packing defined for 6-bit weights`）。
  所以"权重 5/6 bit"这条路当前不通，要么 4 要么 8。

## 6. 建议

| 目标 | 做法 | 代价 |
|---|---|---|
| 只想降输入位宽、不动模型 | **RGB565**，或 **YCbCr 4:2:0 8bit** | ≤0.15 dB（A8），1.6 dB（A12） |
| 尽量压低输入 | **RGB444**（12 bpp） | 0.56 dB（A8），4.7 dB（A12） |
| 不要做 | 灰度、RGB332 | 2.0–2.4 dB（A8），9–19 dB（A12）；色度相关 0.39–0.46 |
| 想提高画质 | 先修 p9（§4.1），再考虑 A10/A12 | A8 上 +4.5 dB 免费；A10 再 +4.2 |
| 想减权重 | 编码器 4 bit、`up3.*.pw` 4 bit；`head.pw` 保持 8 bit | 34.6 % / 18.6 % 权重，−1.0 / −0.2 dB |
| 必须做 | 修 LUT 路径（§4.2） | 当前是常数图 |

**回到原问题**：输入不必是 RGB888，**RGB565 是安全的，RGB444 是下限**；
再低就要接受原图色彩关系丢失。但"对 FPGA 减负"这个目标上，输入位宽的收益很小
（≤2 % line buffer、≤11 % MAC），真正值钱的是 1×1 点卷积的位宽与激活位宽。
